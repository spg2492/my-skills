# Article Template

Write every section as structured, polished prose. Do not use bullet points or lists. Each section should read as a coherent, publication-ready paragraph or set of paragraphs. The only exception is "How to Use It", which uses a numbered sequence where the flow requires it.

### Overview

Introduce the feature and explain what it enables customers to accomplish. Describe the problem it addresses and how it improves the customer's workflow or outcomes. Briefly identify who will benefit most. Provide enough context for customers to understand both what the feature is and why it was introduced, without going into procedural detail. The reader should quickly determine whether the feature is relevant to their needs.

---

### Benefits

Expand on the value the feature delivers. Focus on outcomes such as improving efficiency, reducing manual effort, enhancing personalization, or providing deeper insights. Connect the feature's capabilities to real customer goals and workflows. Clearly explain how the feature helps customers achieve better results. Do not list functionality — write in outcome-focused prose that speaks directly to what the customer gains. Where relevant, draw on customer proof points from pathfactory-context.md.

---

### Prerequisites

*Include this section only if requirements exist. If there are no prerequisites, omit it entirely.*

Outline any requirements that must be met before using the feature. Cover permission requirements, necessary configurations, dependencies on other features, or integration setup. Ensure customers understand any setup needed before they begin.

---

### How It Works

Provide a conceptual explanation of the feature's behavior. Describe the logic behind the feature and how different components interact. Help customers understand what happens when they use the feature and what outputs they can expect. Include a short narrative describing the flow from input to output, building confidence before customers begin using the feature. Do not include step-by-step instructions here.

---

### How to Use It

Walk customers through the primary workflow in a logical order, referencing relevant areas of the interface and explaining what to do at each step. Include brief explanatory context where actions may not be intuitive. Use a numbered sequence where the order of steps is essential. Where screenshots were captured, reference them inline as [Screenshot: filename] so they can be inserted into WordPress at the corresponding step.

---

### Example Use Cases

Demonstrate 2–3 practical scenarios where the feature provides value. Each scenario should reflect a realistic workflow and illustrate how customers can incorporate the feature into their existing processes. Help customers understand when and why they would use the feature, reinforcing the value described earlier in the article. Write each scenario as a short, concrete narrative — not a hypothetical or abstract example.

---

### Important Notes

Highlight key behaviors, dependencies, and limitations customers should be aware of. Clarify default settings, how the feature behaves in different scenarios, and any constraints that may affect usage. Include best practice guidance where relevant to help customers get the most value. Write as direct, factual prose — not warnings or caveats, but useful context that prevents confusion and reduces support inquiries.

---

### FAQs

Address 3–6 common questions customers may have about the feature. Focus on configuration, behavior, permissions, editing capabilities, and limitations. Write each answer as a concise but informative paragraph. The goal is to clarify expected behavior and reduce repetitive support questions.

---

### Availability

Explain how customers can access the feature. Cover release status, plan or tier availability, role-based permissions, or any regional considerations. Ensure customers understand whether the feature is available in their environment and who can use it.

---

## Tone Rules

- Write for B2B marketers and sales professionals, not engineers
- Use "you" language ("you can now...", "your team...", "this gives you...")
- Lead with outcomes, not features
- Be consultative — help the reader understand when and why to use this, not just how
- No jargon: no "payload", "orchestrator", "merge", "sprint", "QA"
- Confident and direct — avoid hedging language like "may", "might", "could potentially"
- Every section must read as polished, publication-ready prose
